# BMA254 accelerometer parity — `bma254`

## 1. Assigned driver and files changed

Driver: Bosch BMA254 accelerometer on the SM-G532M (I2C address `0x18`, I2C3, INT1 = GPIO 3).
Port target: Nura `v7.0.10-mt6735` worktree `$M/worktrees/bma254`, upstream `bmc150-accel` IIO driver.

Files changed (only these two):

- `drivers/iio/accel/bmc150-accel-core.c`
- `drivers/iio/accel/bmc150-accel.h` (one new field `u8 int_latch`)

Upstream ACPI (`BOSC0200`, `DUAL250E`) and OF (`bosch,bma254` and the rest of
`bmc150_accel_of_match`, `bmc150-accel-i2c.c:258-270`) support is preserved; the BMA254
tuning is keyed on `device_is_compatible(dev, "bosch,bma254")`
(`bmc150-accel-core.c:1702`), so every other compatible/ACPI HID keeps the upstream
defaults. `bmc150-accel-i2c.c` is unchanged (compiled for verification only).

A previous agent left partial edits in these two files; they were validated and kept
(chip ID retries, default BW, latch/slope defaults, calibbias plumbing, IRQ wake,
suspend). Changes made on top of that partial work in this run:

1. `in_accel_{x,y,z}_calibbias` sign convention corrected to the Samsung semantics
   `value = acc - caldata` (the chip subtracts 0x38..0x3a from raw data) and the
   incorrect comment claiming IIO "adds calibbias to the raw value" fixed.
2. System suspend now enters low-power mode (PMU_LPW mode bits 2 = the exact register
   value downstream uses for `BMA2X2_MODE_LOWPOWER1`) when the any-motion interrupt is
   armed, instead of leaving the chip in normal mode.

Note on what the patch intentionally does **not** port (documented, no stubs left):

- The Samsung `calibration` sysfs self-calibration *algorithm* (20-sample average,
  1 g z subtraction, `/efs` persistence) is a userspace/HAL policy in the IIO world:
  the same numbers can be computed in userspace and written to
  `in_accel_*_calibbias`. The ROM kernel only applies `acc - caldata` to the samples,
  which the offset registers now reproduce on the data path (and additionally feed the
  any-motion detector, unlike the Samsung software approach).
- The `reactive_alert` sysfs ABI, `poll_delay`/`enable` input-polling ABI and
  `raw_data` input ABI are replaced by the IIO ABI (`sampling_frequency`, buffer
  enable, `in_accel_*_raw`), which is the Nura-wide interface.

## 5. Inferred / hardware-unverified

- **[INFERENCE] Offset register resolution = 1/128 g per LSB**
  (`bmc150-accel-core.c:674-682`). Neither the downstream driver nor the ROM touches
  registers 0x38-0x3A (Samsung calibrates in software), so no program evidence exists
  for the LSB size; this value is not verifiable from the sources available here. All
  calibbias scaling uses it. Hardware check: write known values to 0x38..0x3A and
  measure the shift in raw samples at 2 g/16 g. If the datasheet value differs, only
  the two `DIV_ROUND_CLOSEST` factors need adjusting.
- **[INFERENCE] Slope threshold 5 / duration 1 as defaults**: downstream programs
  these only when the reactive alert is armed (`bma2x2.c:1171-1177`) and never at
  probe; we program them at probe for `bosch,bma254` so the IIO any-motion event
  behaves like the ROM feature out of the box (userspace can still change them via
  the event value/period attributes).
- **[INFERENCE] Low-power mode during suspend is equivalent to the ROM behavior**:
  register value matches downstream exactly (PMU_LPW mode bits 2, `bma2x2.c:620-628`
  LOWPOWER1), and Samsung relies on slope detection in that mode, but wake latency in
  LPM with sleep-duration bits = 0 has not been measured on hardware.
- **Slope-enable axis superset**: we enable slope X|Y|Z (0x07) where the ROM enables
  only slope Z (0x04) — superset, can only wake on motion the ROM would miss. If
  exact ROM wake sensitivity is required, mask the enable bits to `BMC150_ACCEL_INT_EN_BIT_SLP_Z`.
- **IRQ topology**: downstream requests `IRQF_ONESHOT | IRQF_NO_SUSPEND` on a plain
  IRQ and the ROM path holds no wake lock (only `enable_irq_wake`); we use a threaded
  IRQ + `enable_irq_wake`. Wake-on-motion end-to-end (including userspace taking a
  wakeup source before autosleep) is hardware-only to verify.
- **INT pin polarity**: neither downstream (`bma2x2.c`) nor this driver programs
  INT_OUT_CTRL (0x20); both request rising-edge, so the shipped hardware default is
  assumed to work as-is. Left untouched for parity.
- All register values written by the patch come from downstream source as cited in §2;
  no register value was invented.

## 6. DTS fragment (shared DTS not modified)

The shared `arch/arm64/boot/dts/mediatek/mt6737t-samsung-grandpplte.dts` node
(`accelerometer@18`) currently carries

```
mount-matrix = "0", "1", "0",
               "1", "0", "0",
               "0", "0", "1";
```

which maps samples to `(in_y, in_x, in_z)` — determinant -1, i.e. a reflection, and it
matches neither board placement in the ROM. Downstream/ROM `accel_place = 1`
(`rom_dtb_0/1/2.dts`, `sensors_core.c:102` P1 = `(in_y, -in_x, in_z)`). Correct
fragment for the majority placement (rows are `[out_x out_y out_z]`, `out = M * in`):

```dts
&i2c3 {
	accelerometer@18 {
		mount-matrix = "0", "1", "0",
				"-1", "0", "0",
				"0", "0", "1";
	};
};
```

For the board variant matching `rom_dtb_3.dts` (`bma2x2,accel_place = <0x05>`,
P5 = `(-in_y, -in_x, -in_z)`):

```dts
&i2c3 {
	accelerometer@18 {
		mount-matrix = "0", "-1", "0",
				"-1", "0", "0",
				"0", "0", "-1";
	};
};
```

Note: the ROM applies this remap inside the kernel before handing samples to the HAL;
with IIO the kernel only publishes `in_accel_mount_matrix` and userspace must apply it.
The correct matrix for the target board must be selected (the ROM picks the DTB per
board revision at boot).
