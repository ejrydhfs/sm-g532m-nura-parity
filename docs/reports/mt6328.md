## 2. Evidence: downstream source and ROM

Primary reference: `$M/src/downstream-grandpplte` (Samsung GPL kernel for

### 2.1 RTC register map and write-protect

* Downstream `drivers/misc/mediatek/include/mt-plat/mt6735/include/mach/mtk_rtc_hal.h:36`
  `RTC_BASE = 0x4000` and `:26` `RTC_INTERRUPT_NUM = 9` -> MT6328 RTC registers at
  0x4000, PMIC IRQ line 9.
* Downstream `mach/mt_rtc_hw.h:244-246` `RTC_PROT = RTC_BASE+0x0036`,
  `RTC_PROT_UNLOCK1 0x586a`, `RTC_PROT_UNLOCK2 0x9136`; `:264`
  `RTC_WRTGR = RTC_BASE+0x003c`.
* Downstream `drivers/misc/mediatek/rtc/mtk_rtc_hal_common.c:69-72`
  `rtc_write_trigger()`: write `RTC_WRTGR=1`, poll `RTC_BBPU.CBUSY`;
  `:75-81` `rtc_writeif_unlock()`: PROT=UNLOCK1, trigger, PROT=UNLOCK2, trigger.
  `mtk_rtc_common.c:809-825` `rtc_late_init()` calls it once and leaves the
  interface unlocked.
* ROM disassembly confirms identical behavior:
  * `rtc_writeif_unlock` @ `0xc039d1a0`: `movw r1,#0x586a; movw r0,#0x4036`
    (PROT=0x4036), `mov r1,#1; movw r0,#0x403c` (WRTGR=0x403c), `bl
    rtc_busy_wait`, then `0x9136 -> 0x4036`, `1 -> 0x403c`, `rtc_busy_wait`.
  * `hal_rtc_set_alarm` @ `0xc039e03c`: `hal_rtc_set_alarm_time()`, then
    `RTC_IRQ_EN (0x4004) |= 5` (`RTC_IRQ_EN_ONESHOT_AL`), then `rtc_write_trigger`.
  * `hal_rtc_clear_alarm` @ `0xc039e06c`: `RTC_IRQ_EN (0x4004) &= ~BIT(0)`,
    `RTC_PDN2 (0x402e) &= ~BIT(4)` (`PWRON_ALARM`), **then** `rtc_write_trigger`,
    **then** read-clear `RTC_IRQ_STA (0x4002)`, then reprogram alarm time.
* ROM kallsyms (`zip/symbols.txt`): `rtc_write_trigger`, `rtc_writeif_unlock`,
  `hal_rtc_get_alarm`, `hal_rtc_set_alarm`, `hal_rtc_clear_alarm`,
  `hal_rtc_is_lp_irq`, `hal_rtc_save_pwron_alarm`, ... all present.

### 2.2 IRQ numbering (mt6328 core.h)

* Downstream `upmu_hw.h` `MT6328_PMIC_RG_INT_STATUS_*` fields: STATUS0 shifts
  0-7,9,10,12-15; STATUS1 shifts 0-2,5,8-14; STATUS2 shifts 0-14 (of
  `MT6328_INT_STATUS0/1/2` at 0x02c4/0x02c6/0x02c8).
* Nura `drivers/mfd/mt6397-irq.c:46-47` maps `hwirq` as bit index across the
  three 16-bit status registers (`reg = hwirq >> 4`, `shift = hwirq & 0xf`), so
  the enum must be bit-indexed. The old sequential enum put RTC at 8 instead of
  9; the fixed values match `MT6328_PMIC_RG_INT_STATUS_RTC_SHIFT = 9`
  (upmu_hw.h:2657-2659) and downstream `RTC_INTERRUPT_NUM = 9` (mtk_rtc_hal.h:26).

### 2.3 Regulator rails, tables, enable/vosel registers

* Downstream `power/mt6735/pmic.c:1115-1155` `mtk_ldos[]` (28 LDOs) and
  `:1157-1163` `mtk_bucks[]` (5 bucks) enumerate every rail;
  `upmu_sw.h:122-152` `MT65XX_POWER` enum is the same list. The Nura
  `mt6328_regulators[]` covers all 33 rails (5 bucks + 28 LDOs).
* Every enable/VOSEL register + mask in the Nura array was checked against
  `upmu_hw.h` field definitions (e.g. `RG_VIBR_EN` = `MT6328_VIBR_CON0` bit 1,
  `RG_VIBR_VOSEL` = `MT6328_DLDO_ANA_CON2` mask 0x7 shift 4;
  `RG_VSRAM_EN` = `MT6328_LDO_VSRAM_CON0` bit 1, `RG_VSRAM_VOSEL` =
  `MT6328_SLDO_ANA_CON9` mask 0x7f shift 0). All match after the fixes below.
* **VPROC fix (from previous partial work, validated):** `upmu_hw.h`
  `MT6328_PMIC_VPROC_VOSEL_ADDR = MT6328_VPROC_CON11` (base tree wrongly used
  `MT6328_VPA_CON11`, a copy-paste bug that programmed VPA for VPROC).
* **VCAMIO fix (validated):** base tree listed `ldo_vcamio` twice (duplicate
  designated initializer); second entry removed.
* **VSRAM fix (validated):** enable register corrected to
  `MT6328_LDO_VSRAM_CON0` (0x0a40) per `MT6328_PMIC_RG_VSRAM_EN_ADDR`; base used
  `MT6328_VSRAM_CON9` (0x04ae).
* **VRF18_1 mask:** downstream `mtk_regulator_set_voltage_sel()` (pmic.c:778-805)
  writes selector 4 (1.825 V, `mt6328_VRF18_1_voltages[]` pmic.c:1078-1083)
  through `pmic_config_interface(SLDO_ANA_CON4, 4, 0x3, 4)`; since
  `pmic_config_interface()` (pmic.c:218-256) ORs `val << SHIFT` **unmasked**,
  selector 4 reaches bit 6. Nura previously used mask 0x30 which dropped
  selector 4 to 0x00 (1.2 V); widened to 0x70 (3-bit field) to reproduce the
  downstream bit pattern. ROM `mtk_regulator_set_voltage_sel` @ `0xc039f8d4`
  disassembly agrees: `cmp r6,#4; beq -> pmic_config_interface(0xa86, 0, 1, 2)`
  else `(0xa86, 1, 1, 2)` — i.e. clear `SLDO_ANA_CON8` bit 2 only for 1.825 V.
* **VEFUSE (validated, no change):** downstream writes `selector+3` into
  `RG_VEFUSE_VOSEL` (pmic.c:798-805; ROM @ `0xc039f9a0: add r1, r6, #3`), so
  hardware codes 3-7 carry 1.8-2.2 V. The Nura `ldo_volt_table3` (0-padded
  8-entry table) already encodes exactly that mapping.
* **VCAMD trim remap (new):** downstream `mtk_regulator_set_voltage_sel()`
  (pmic.c:786-795) calls `upmu_set_rg_vcamd(1)` for selector 3 (1.2 V) and
  `upmu_set_rg_vcamd(0)` otherwise; `upmu_set_rg_vcamd()` (pmic.c:499-513) writes
  `RG_VCAMD_CAL` = `mt6328_vcamd[vcamd_cal]` or the cached factory trim
  (`vcamd_cal` cached at pmic.c:1471). `mt6328_vcamd[]` (pmic.c:494-497) =
  `{1,2,3,4,5,6,7,7,9,10,11,12,13,14,15,0}`. ROM confirms: strcmp "VCAMD"
  (string @ `0xc0c29fe0`), `cmp r6,#3; beq upmu_set_rg_vcamd(1)`, else
  `pmic_set_register_value(PMIC_RG_VCAMD_CAL, vcamd_cal)`. Ported into
  `mt6328_ldo_table_set_voltage_sel()`; trim cached at probe.
* **VMC E1 OTP table quirk (new):** downstream `mtk_regulator_init()`
  (pmic.c:1458-1467): if `PMIC_SWCID == PMIC6328_E1_CID_CODE (0x2810, pmic.h:23)`
  and `pmic_read_VMC_efuse() != 0` use `mt6328_VMC_E1_2_voltages`
  (1.3/1.8/2.9/3.3 V) else `mt6328_VMC_E1_1_voltages` (2.5/2.9/3.0/3.3 V);
  otherwise the default `mt6328_VMC_voltages` (1.8/2.9/3.0/3.3 V).
  `pmic_read_VMC_efuse()` (pmic.c:520-550) is reproduced bit-for-bit (efuse
  clock ungated via `RG_EFUSE_CK_PDN_HWEN`/`RG_EFUSE_CK_PDN`, `RG_OTP_RD_SW=1`,
  `RG_OTP_PA = 0xd*2 = 0x1a`, toggle `RG_OTP_RD_TRIG`, poll `RG_OTP_RD_BUSY`,
  read `RG_OTP_DOUT_SW`, restore clocks). ROM `pmic_read_VMC_efuse` @
  `0xc039f9f0` disassembly confirms the same sequence and constants (flag
  writes 0x1ac/0x164/0x700/0x6f5, `r1=0x1a`, toggle of 0x6fd, poll 0x702, read
  0x701, `lsl r0, r4, #7` return). ROM kallsyms also contains
  `mt6328_VMC_E1_1_voltages`, `mt6328_VMC_E1_2_voltages`.
  One deliberate deviation: the busy poll is bounded (1000 x 10 us -> `-ETIMEDOUT`)
  instead of the downstream infinite `while` loop.

### 2.4 Vibrator rail

* Downstream `pmic.c:1145` `PMIC_LDO_GEN1(VIBR, PMIC_RG_VIBR_EN,
  PMIC_RG_VIBR_VOSEL, mt6328_VCAM_AF_voltages, ...)`: VIBR shares the VCAMAF
  table (1.2/1.3/1.5/1.8/2.0/2.8/3.0/3.3 V). Nura `ldo_vibr` uses
  `ldo_volt_table9` = same values; enable `MT6328_VIBR_CON0` bit 1 and VOSEL
  `MT6328_DLDO_ANA_CON2` mask 0x70 match `upmu_hw.h`
  (`MT6328_PMIC_RG_VIBR_EN_*`, `MT6328_PMIC_RG_VIBR_VOSEL_*`).
* ROM DTB (`zip/rom_dtb_0.dtb`): `ldo_vibr { regulator-name = "vibr";
  regulator-min-microvolt = <0x325aa0>; regulator-max-microvolt = <0x325aa0>; }`
  (3.3 V fixed) and consumer `sec_vib { sec_vib,regulator = "vibr";
  sec_vib,ldo_type = <0>; sec_vib,max_timeout = <0x2710>; }`. Nura's
  `mt6328.dtsi` `ldo_vibr` node already matches the ROM (3.3 V fixed) — no
  change required on the rail or in DTS.
* Note: the downstream vibrator HAL comment (`vibrator/mt6735/vibrator.c:44-53`)
  and `vibrator.h` enum disagree with the PMIC table at code 4 (2.5 V vs 2.0 V).
  The PMIC table (used by the shipped regulator code and ROM binary) is kept.

## 5. Inferred / hardware-unverified

Marked `[INFERENCE]` where the source/ROM evidence is indirect:

* `[INFERENCE]` **VRF18_1 VOSEL field width**: `upmu_hw.h` declares the
  `RG_VRF18_1_VOSEL` mask as 0x3, but downstream writes selector 4 unmasked
  through `pmic_config_interface()` (which ORs `val << shift` without masking),
  reaching `SLDO_ANA_CON4` bit 6. The driver therefore treats the field as 3-bit
  (mask 0x70) to reproduce the downstream bit pattern. Whether bit 6 is truly
  part of VOSEL on silicon is hardware-unverified.
* **VMC E1 OTP quirk**: correct on E1 (SWCID 0x2810) silicon only; table choice
  depends on OTP word 0xd as read by the PMIC. Untested on hardware; the
  bounded busy-poll timeout path (10 ms) is untested.
* **VCAMD trim remap**: the `mt6328_vcamd[]` remap and the cached factory trim
  are ported verbatim from downstream; effect on actual VCAMD accuracy is
  hardware-unverified.
* **RTC write-protect unlock at probe**: downstream unlocks at `late_initcall`;
  unlocking at probe is equivalent for all post-probe RTC ops but timing
  relative to the bootloader's use of RTC spare registers is hardware-unverified.
* **Alarm clear ordering**: clear/trigger/read-clear sequence matches the ROM
  binary exactly (§2.1) but alarm re-fire suppression is untested on hardware.
* Everything in this patch is source-level parity only; no phone is attached.

## 6. DTS fragment

The shared `arch/arm64/boot/dts/mediatek/mt6328.dtsi` is not edited. To
instantiate the RTC, add this child node to the `mt6328` PMIC node (or include
this overlay):

```dts
&mt6328 {
	rtc {
		compatible = "mediatek,mt6328-rtc";
	};
};
```

Notes:
* The MFD cell supplies the register window (0x4000, 0x40) and the PMIC IRQ
  (hwirq 9); no `reg`/`interrupts` properties are needed (same shape as the
  upstream `mediatek,mt6397-rtc` node in `mt8173-elm.dtsi:1108`).
* Without this node the RTC platform device is created without an `of_node` and
  `rtc-mt6397` probe now fails cleanly with `-ENODEV` instead of dereferencing a
  NULL `rtc->data`.
* No vibrator DTS change is needed: `mt6328.dtsi` `ldo_vibr` (3.3 V fixed)
  already matches the ROM DTB.
